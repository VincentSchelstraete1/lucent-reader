## Key finding up front

The architectural convergence described in the migration plan (one `learn_runtime.process_tutor_event()` entry point, one persisted `state.currentScene`, no legacy step-cursor authority) **had already mostly happened** before this session started -- the old cursor-based functions were present but dead (unreachable, guarded by `elif False` or literally inside an unreachable docstring). The user-visible breakage was not "competing architectures" so much as **concrete wiring/logic bugs inside the already-converged runtime**, several of them severe. This handoff documents those bugs and their fixes, plus what's still open.

## Bugs found and fixed (all confirmed live via the Playwright driver, not just unit tests)

Commit `8c0abe5` (backend) and `05e0462` (frontend) on `feature/public-auth-flow` contain these. Nothing has been pushed.

1. **Repeated questions** -- `learn_runtime._private_for_rendered_scene()` built the persisted grading state (`state.currentScenePrivate.interaction`) from the scene block's *public* `LearnStepView`, which lacks answer-bearing fields (`answerId`, `acceptedAnswers`, `correctOrder`, `matches`, `answerMap`, ...), whenever a practice block existed in the rendered scene -- which is always. Any answer to a generated remediation step could therefore never be graded (`_coerce_step` would fail validation), so `current` stayed `None`, evidence never advanced, and the runtime kept regenerating a new but textually-identical remediation prompt. **Fix:** reordered priority to use the executor's own selected step object (or the objective's authored candidate by ID) before ever falling back to coercing the public view.

2. **Continue dead-ends** -- once an objective's candidate pool was exhausted (all authored steps answered/used), `process_tutor_event` persisted an inert scene (no practice, same content) and returned -- Continue would just bump the revision forever with nothing visibly changing, and never transitioned to another objective or completed the session. **Fix:** added `_advance_objective_or_complete()`, called from both exhaustion branches (correct-but-nothing-left, and needs-review-after-3-attempts).

3. **Objective oscillation** (found *during* verifying fix #2) -- the first version of the fix picked "any objective that isn't DEMONSTRATED," which doesn't check whether that objective itself has remaining candidates. Two simultaneously-exhausted objectives bounced the learner back and forth between them forever (confirmed live: 10+ consecutive alternations, zero progress). **Fix:** added `_objective_has_remaining_candidates()` and required it in objective selection.

4. **Duplicate objective-selection logic** -- there was already an unused `select_target_objective()` function built for exactly this purpose (never wired in). Consolidated: `select_target_objective()` now takes `exclude_concept_id`, checks remaining candidates, and prioritizes the revisit queue; `_advance_objective_or_complete()` calls it instead of duplicating the logic inline.

5. **Evidence silently discarded on the exhaustion turn** -- `_advance_objective_or_complete()` (and the pre-existing "needs_review" branch it replaced) never committed the caller's in-memory `state` mutations onto `session.state` before calling `persist_scene_revision()`, which internally re-reads `session.state` from scratch. A response that happened to exhaust the last candidate had its own graded evidence (attempts/correct/incorrect counters) thrown away. **Fix:** `session.state = state` at the top of `_advance_objective_or_complete()`.

6. **Agentic adaptation invisible** -- `LEARN_TUTOR_MODEL_ENABLED` defaults off; nothing in the repo ever set it. Every tutor decision, diagnosis, and Ask Lucent call silently used the deterministic fallback regardless of the valid `ANTHROPIC_API_KEY`. **Fix:** documented above (env var, not code) -- but this exposed a real risk: enabling it made the **existing test suite start hitting the live network** (tests went from ~26s to ~157s), because nothing forced it off for tests. **Fix:** `backend/tests/conftest.py` now force-sets `LEARN_TUTOR_MODEL_ENABLED=0` alongside its other environment overrides.

7. **Ask Lucent / hints answer about the wrong objective** -- `ask_lucent()` and `get_learn_hint()` both resolved "the active objective" from `session.objective_index`, a legacy DB column the authoritative runtime never writes (frozen at 0 from session creation). Confirmed live: after the runtime moved on to "Momentum," Ask Lucent's "explain this differently" answered about "Newton's Second Law" instead. **Fix:** both now resolve from the persisted scene's actual `objective_id` (or `state.currentObjectiveId`), falling back to the stale column only if that lookup somehow fails.

8. **"Objective X of Y" progress frozen** -- same root cause as #7: `_session_payload()`'s `objectiveIndex` field read the stale DB column directly, so the UI progress indicator never advanced even as the learner genuinely moved through objectives. **Fix:** derive it from the active scene's objective position in the plan.

9. **Internal grading language leaking into public feedback** -- confirmed live: after a wrong answer, the displayed "feedback" was `"The learner's response ... directly states that their answer is unrelated ... This is a complete non-response ... rather than evidence of a specific misconception."` -- verbatim LLM grading rationale, third-person and analytical, exactly what the migration plan's Phase 8 forbids ("internal tutor metadata never renders directly"). Root cause: `process_tutor_event` used `evaluation.evidence` (the model's internal rationale field) directly as public feedback text. **Fix:** added `LearnEvaluation.student_message` (alias `studentMessage`), a new required field in the model's structured-output schema, explicitly instructed to be natural/second-person and never describe or quote the learner's response; `process_tutor_event` now prefers it over `evidence` for public feedback. Added a durable regression guard in `learn_agent_scenarios/harness.py`'s `assert_trace_invariants()`: public feedback text must never contain "the learner" or "non-response".

10. **Stale feedback survives an objective transition** (found *during* re-verifying fix #9) -- confirmed live: after transitioning from Newton's Second Law to Momentum, the feedback shown still read "Let's start fresh with Newton's Second Law..." even though the visible content was about Momentum. Root cause: `_advance_objective_or_complete()` didn't clear `state.lastFeedback`/`lastFeedbackKind`, and `_session_payload()` falls back to those when no explicit feedback is passed. **Fix:** clear both at the top of `_advance_objective_or_complete()`. **This fix has not yet been re-verified live** -- the browser run in flight when this handoff was written started before the fix; check its results (see "Immediate next action" below) and re-run if it doesn't show the fix taking effect (the run started with the fix in the server process already, since the server auto-reloads and the fix landed before the run's "I don't know" step -- but confirm from the actual log rather than assuming).

11. **Repeated generic remediation phrasing** -- the very first repair-generation fix (before contrastive remediation existed) always produced the identical templated short-answer prompt regardless of how many times it regenerated, which read as "the same question" to a real user even though each had a distinct ID. **Fix:** added phrasing variety by attempt number (short_answer -> teach_back), then superseded by #12 below for structured-answer failures specifically.

12. **No targeted contrastive remediation in the live runtime** -- `_append_remediation()` (a dead router function, plan-mutating, never called live) had real per-type contrastive logic (e.g., for a wrong `matching` answer, build a multiple-choice question naming the two actually-compared mechanisms) that was strictly better than the live runtime's generic fallback, but was unreachable and also violated plan invariant #11 (never mutate `LearnPlan.objectives[].steps[]`). **Fix:** extracted the pure content-generation logic into `learn_engine.build_remediation_step(objective, failed_step, repair_id)` (no plan mutation -- the caller owns ID/placement), wired it into `process_tutor_event`'s exhaustion branch as the preferred path for `multiple_choice`/`prediction`/`matching`/`ordering`/`labeling` failures on the first remediation attempt, falling back to the generic short_answer/teach_back generation otherwise.

13. **Focus Mode's Ask Lucent panel rendered off-screen** -- confirmed via screenshot: `.learn-focus-mode .learn-scene-shell > .learn-ask-lucent { position: absolute; left: calc(50% + 520px); width: 260px; }` put the panel well past the right edge of the viewport at essentially all normal widths (the media-query breakpoint meant to fix this, `max-width: 1260px`, didn't match the actual overflow math, which needed roughly 1650px+ to not clip). Also found a fully dead duplicate rule (`.learn-focus-mode .learn-scene-shell` declared twice with conflicting layout models, plus a `.learn-focus-mode > .learn-ask-lucent` rule that could never match the actual DOM shape) -- exactly the "features disappear when other fixes land" pattern the user described, from CSS patches stacking without removing what came before. **Fix:** replaced with one responsive CSS grid (`minmax(0,1fr) minmax(260px,320px)`, collapsing to one column under 1000px).

14. **Visual stage never persisted** -- `StructuredVisual`'s Previous/Next stage navigation was purely local React state; `POST /learn-sessions/{id}/visual-events` existed on the backend but nothing on the frontend ever called it. Refresh would not restore the exact visual stage, failing the plan's explicit acceptance requirement. **Fix:** added an `onStageChange` callback prop to `StructuredVisual`, wired in `Notes.tsx::LearnView` to call `api.learnVisualEvent(...)` and merge the resulting session back in.

15. **No focus transfer after a scene revision** -- the plan's Focus Mode requirements include "focus transfer to new scene heading after revision," which was entirely unimplemented (no accessibility cue that content changed after a response, particularly important in Focus Mode which has no scroll/other signal). **Fix:** added a `headingRef` + `useEffect` keyed on `session.scene.id`/`revision` that calls `.focus()` on the (now `tabIndex={-1}`) scene heading.

This was a live crash risk if anyone ever "fixed" the `False` literal without checking. Removed entirely.

(Note: this means true within-session delayed review -- re-serving a concept from the revisit queue with a different representation before the session ends -- is **still not implemented**; see "Known gaps" below. `completion_met()` was *not* removed -- it's now used to distinguish `ended_reason="evidence_sufficient"` from `"objectives_exhausted"` when a session completes.)

## Current architecture (confirmed, as of this checkpoint)

- **One authoritative entry point** for response/continue events: `learn_runtime.process_tutor_event()`, called from `routers/learn.py::submit_learn_response()`. No cursor-based branch is reachable in production code.
- **One persisted scene**: `session.state.currentScene` (Pydantic `LearningScene`), read via `learn_runtime.load_current_scene()`. `_session_payload()` (the GET/response serializer) only ever serializes it -- it does not recompose.
- **One grading state**: `session.state.currentScenePrivate` (`ScenePrivateState`), built exclusively by the (now-fixed) `_private_for_rendered_scene()`.
- **`step_index` is gone** (dropped from the DB in a prior migration; not on the `LearnSession` model at all). `objective_index` remains a DB column but is now correctly treated as **write-once-at-creation, read-never-for-content** -- every place that needs "the active objective" resolves it from the persisted scene/`currentObjectiveId`, never from this column. The column itself is not removed (matches the plan's "derived reporting/compatibility column" framing), but nothing depends on it being accurate anymore, including the derived `objectiveIndex` field returned to the frontend (now computed fresh each request).
- **Ask Lucent** persists through the same `learn_runtime.persist_scene_revision()`/`apply_scene_message()` used by normal responses (one scene, one owner), but its *decision-making* is a separate code path in `routers/learn.py::ask_lucent()` rather than routing through `process_tutor_event(ASK_LUCENT)` as the plan's Section 3.2 describes. This was evaluated and deliberately left as-is for this pass (see "Known gaps / deliberately not done").
- **Visual state**: canonical owner is `state.currentScene.visualState`; no competing `state.visualStage`/`state.visualHighlight` production writes exist. The frontend now actually persists stage changes through it (fix #14).
- **Tutor model**: real Anthropic calls now active (`LEARN_TUTOR_MODEL_ENABLED=1` locally), confirmed live via the browser driver -- genuinely different pedagogical text and interaction choices observed across turns, not just deterministic fallback.

## Known gaps / deliberately not done this pass

These were identified but intentionally left alone, per the instruction to treat the plan as goals and not rewrite for architectural purity alone. Revisit if continuing into Phases 3-9 more deeply:

1. **Ask Lucent decision-making is a separate code path**, not routed through `process_tutor_event(ASK_LUCENT)`. The plan's Section 3.2/5.0 wants one shared observation/decision/executor path for both normal responses and Ask Lucent. Currently `ask_lucent()` in the router builds its own `TutorObservation`/`TutorDecision`/scene mutation using `_tutor_observation()` (a router-local function, still live and correctly used) and `apply_scene_message()`. This works and shares the persistence layer (one scene), so it's not producing the regressions seen -- but it is real logic duplication. Folding it into `process_tutor_event` would be a moderate refactor (the event-type dispatch inside `process_tutor_event` would need an `ASK_LUCENT` branch that preserves active practice unless the decision explicitly replaces it, per plan Section 3.2). Not attempted this pass.
2. **`AuthorizedAssetCatalog` / typed `SceneOperation` discriminated-union model** (plan Section 4.2/4.1) was never built. The live runtime still passes `TutorDecision.scenePlan.blocks`/`actions` (the older, less-typed shape) through `compose_learning_scene()`. This is a larger schema/executor rewrite than was in scope for bug-fixing; the current shape works and is exercised by real tests, but doesn't match the plan's target typed-operation contract. Not attempted.
3. **True within-session delayed review** is not implemented: a concept that lands in `revisitQueue` with `NEEDS_REVIEW` gets priority if another *not-yet-exhausted* objective transition happens to land on it (via the consolidated `select_target_objective()`), but there's no dedicated "come back to this concept later in the same session with a different representation" cycle (plan Section 3.6 / acceptance table's "Scaffold fading"/review rows). `apply_review_schedule`/`select_due_review` (unused, removed) were a first attempt at this that never got wired in.
4. **`web/src/learn/*` file structure** from the plan's Section 6.1 (extracting `useLearnSession.ts`, `LearningSceneView.tsx`, `LearnInteractionView.tsx`, etc. as separate files/modules) was never done -- everything still lives in `web/src/pages/Notes.tsx` as one large file. The *behavior* the plan wants (scene-only rendering, no `session.step`/`session.action` reads) is already satisfied (`grep` confirms zero such reads), so this is purely an organizational deviation, not a functional gap. Not attempted -- splitting a large working file immediately before final verification would add risk for no behavioral benefit.
5. **Typed `SceneOperation`/`TutorContentBlockDraft` replacing free-form `TutorToolCall.arguments: dict`** (plan Section 4.2, Phase 9 deletion target) -- still free-form, still validated by the existing allowlist/argument-key checks in `choose_tutor_decision()`, not by a Pydantic discriminated union. Not attempted.
6. **`response`/`feedback`/`action`/`evaluation` public fields on `LearnSessionResponse`** are still present (plan Phase 9 wants them removed once the frontend is scene-only, which it already is). Not removed this pass -- low risk either way, but technically still-present deprecated surface.

None of these six gaps were observed to cause the regressions this session was asked to fix (repeated questions, dead-ends, invisible adaptation, Ask Lucent inconsistency, focus/fullscreen regressions) -- they are pre-existing, real, but lower-priority relative to what's already been fixed and verified.
